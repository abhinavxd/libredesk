# Contributing to libredesk

Thanks for your interest in contributing to libredesk.

## Before you start

* New features need clear user demand or a demonstrated practical need. An idea sounding useful or being easy to generate with AI isn't enough reason to add it.
* All contributions should align with the project's scope, goals, and technical direction.
* Bug fixes and documentation improvements can go straight to a PR without prior discussion.
* New features and larger changes should start with an issue before implementation.
* Keep changes focused on a single concern wherever possible.
* For translations, please contribute through [Crowdin](https://crowdin.com/project/libredesk) instead of opening PRs for translation changes.

## Pull requests

Every feature adds code that needs ongoing maintenance and support. Avoiding feature bloat helps keep libredesk usable and maintainable as it grows.

Reviewing a PR can take more time than writing it. Maintainers need to understand the code and check its effects on existing behavior. Changes must follow existing conventions and account for their effects on performance, usability, and stability.

A working implementation alone doesn't guarantee that a change belongs in libredesk. Whether a PR is accepted, and on what timeline, is ultimately up to the maintainers. Discussing larger changes first helps avoid spending time on work the project cannot accept.

Before opening a pull request, please follow these guidelines:

1. Open an issue before implementing a new feature or larger change. Explain the problem, who needs the change, and how you plan to implement it, including relevant technical details. The change may already be in progress or fall outside the project's direction.
2. Keep PRs small and focused on a single concern. Smaller PRs are easier to review and test thoroughly. Bundling multiple features into one PR is strongly discouraged.

Thanks for helping keep libredesk focused and maintainable.
